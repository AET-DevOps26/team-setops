# 🗄️ Database Schema Documentation

DevPulse currently utilizes a shared **PostgreSQL** database named `appdb`. Following microservice principles, while the services share a physical database instance for local ease of use, they manage their own independent tables. 

Data correlation across services is achieved using a cross-system `logId` (UUID) generated at the point of ingestion, rather than hard database foreign keys.

---

## Table: `system_logs`
**Owning Service:** `spring-logbook`  
**Purpose:** Stores immutable, historical records of all ingested system events, deployment logs, and errors. 

| Column Name | Data Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `log_id` | `UUID` | **PRIMARY KEY** | The unique correlation ID generated by `spring-ingestion`. |
| `service_name` | `VARCHAR(255)` | `NOT NULL` | The name of the microservice or system that emitted the log. |
| `type` | `VARCHAR(255)` | `NOT NULL` | The category of the log (e.g., `DEPLOYMENT_LOG`, `SYSTEM_ALERT`). |
| `severity` | `VARCHAR(255)` | `NOT NULL` | The severity level of the event (e.g., `INFO`, `WARN`, `ERROR`). |
| `log_content` | `TEXT` | `NULLABLE` | The detailed message, stack trace, or payload of the log. |
| `timestamp` | `TIMESTAMPTZ` | `NOT NULL` | The exact UTC timestamp when the event occurred. |

---

## Table: `incident_status`
**Owning Service:** `spring-alerts`  
**Purpose:** Tracks the lifecycle state of specific incidents that have triggered an alert via the rules engine.

| Column Name | Data Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `log_id` | `UUID` | **PRIMARY KEY** | The unique correlation ID mapping back to the exact log that triggered the alert. |
| `status` | `VARCHAR(50)` | `NOT NULL`, `DEFAULT 'ACTIVE'` | The current lifecycle state of the incident (e.g., `ACTIVE`, `RESOLVED`, `IGNORED`). |

---

## 🏗️ Architectural Notes

* **Decoupling over Foreign Keys:** Notice that there is no explicit `FOREIGN KEY` constraint linking `incident_status.log_id` to `system_logs.log_id`. This is an intentional microservices design choice. `spring-alerts` and `spring-logbook` are completely decoupled; they process messages asynchronously via RabbitMQ and do not depend on each other's database transactions to succeed.
* **JPA Auto-DDL:** In local development (as defined in `application.yml`), Spring Data JPA's `hibernate.ddl-auto: update` is used. This automatically generates and alters the tables based on the `Log` and `IncidentStatus` Java entities on startup.
